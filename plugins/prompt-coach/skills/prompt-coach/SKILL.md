사용자의 거친 요청을 구조화된 요청으로 바꿔 보여 주고, 승인받은 뒤 실행한다.

## 입력

- `/prompt-coach` 뒤에 쓴 글, 또는 바로 앞에 쓴 요청.
- 입력이 없으면 "다듬을 요청을 `/prompt-coach` 뒤에 적어 주세요."라고만 안내한다.

## 절차

1. 요청과 대상 코드·파일을 먼저 읽는다. 대상이 모호하면 작업 폴더의 최근 수정 파일, 열려 있는 파일, 앞선 대화에서 찾는다.
2. 요청에서 아래 다섯 항목을 뽑는다. **ROLE 은 사용자가 말하지 않아도 직접 판단해 정한다.** 나머지 항목은 입력에 없는 내용을 지어내지 않는다.
   - `[ROLE]` 코드·파일·요청에서 판단한 가장 알맞은 전문가 역할과 중점. `역할 — 중점 (근거: ...)` 형식으로 쓴다.
     - 판단 근거 예: 사용 언어·프레임워크(FastAPI·DB 쿼리 → 시니어 백엔드 엔지니어, torch·YOLO → ML 엔지니어, README·보고서 → 기술 문서 작성자), 요청의 성격(느리다·메모리 → 성능 최적화, 에러·안 돌아감 → 원인 분석·디버깅, 쉬운 설명 → 교육).
     - 근거가 약하면 가장 가능성 높은 역할을 고르되 근거에 "추측"이라고 밝힌다.
   - `[GOAL]` 얻고 싶은 결과
   - `[CONSTRAINTS]` 지켜야 할 조건 (언어, 범위, 수정 허용 여부, 금지 사항)
   - `[CONTEXT]` 관련 파일·에러·현재 상태 (코드·문서로 확인 가능한 건 묻지 말고 직접 확인한다)
   - `[QUESTION]` 정확한 요청 한 문장
3. 비어 있는 항목 중 **결과를 좌우하는 것만** 최대 3개까지 되묻는다. 우선순위는 CONTEXT > CONSTRAINTS > GOAL 이다. ROLE 은 묻지 않고 직접 판단한다. 다 알 수 있으면 묻지 않는다.
4. 정리본을 아래 출력 형식으로 보여 주고 "이대로 진행할까요?"라고 묻는다. 맨 위에 "제 역할은 ~이고 ~ 중심으로 답하겠습니다."를 한 줄 먼저 밝힌다.
5. 사용자가 승인하면 정리된 요청대로 실행한다. 역할이나 중점이 틀렸다고 하면 그 부분만 고쳐 다시 보여 준다.

## 학습 기록

요청을 정리할 때마다 어떤 항목이 비어 있었는지 기록해 두고, 쌓인 기록으로 사용자의 습관을 알려 준다. 세션이 바뀌어도 남는 것이 이 스킬의 핵심 가치다.

- **기록하기**: 정리본을 보여 준 직후, 아래 명령으로 1건을 기록한다. `missing`에는 사용자 입력에 **실제로 없었던** 항목(`GOAL`, `CONSTRAINTS`, `CONTEXT`)만 넣는다. 큰 요청이면 `big`을 true 로 한다.
  ```
  echo '{"original":"<원래 입력>","missing":["CONTEXT"],"big":false,"score":3}' | python "<스킬 폴더>/scripts/ask_log.py" add
  ```
  - `<스킬 폴더>`는 스킬이 호출될 때 안내되는 "Base directory for this skill" 경로다. `python`이 없으면 `python3`을 쓴다. Python 이 아예 없으면 기록·통계만 건너뛰고 그 사실을 알린다.
  - 입력에 작은따옴표가 있으면 heredoc 으로 넘긴다. 긴 로그·코드는 스크립트가 앞 200자만, 비밀정보는 `***`로 가려 저장한다.
  - 출력은 `기록됨 (총 N건)` 한 줄만 덧붙인다. 기록 실패는 숨기지 않고 알린다.
- **통계 보기**: 사용자가 `/prompt-coach 통계`, `/prompt-coach 내 습관`, "내가 뭘 자주 빠뜨려?"라고 하면 요청 정리 대신 아래를 실행해 결과를 쉬운 말로 풀어 준다.
  ```
  PYTHONIOENCODING=utf-8 python "<스킬 폴더>/scripts/ask_log.py" stats
  ```
  - 평균 전달력과 이전 대비 변화(있을 때)를 먼저 알려 주고, 가장 자주 빠뜨리는 항목 1~2개를 짚고, **그 항목을 채우는 구체적인 한 문장 예시**를 준다.
  - 기록이 5건 미만이면 "경향을 판단하기는 이릅니다"라고 밝히고 단정하지 않는다.
- 기록 파일은 사용자 홈의 `.claude/ask-log.jsonl`이다. 처음 기록할 때 이 위치를 한 번 알려 준다. 지우면 기록이 초기화된다.

## 긴 로그 처리

로그가 길게(대략 100줄 이상) 붙여지거나 로그 파일 경로가 오면 전체를 분석하지 않고 관련 부분만 추려서 `[CONTEXT]`에 넣는다.

- **추리는 방법**
  - 파일 경로면 Read 로 통째로 읽지 말고 Grep(`-n`, 앞뒤 `-C 5`)으로 `error|exception|traceback|fail|critical|fatal|warn|killed|oom|cuda` 를 찾는다.
  - 붙여넣은 글이면 같은 키워드로 훑고, 줄 번호는 **붙여넣은 글 기준**이라고 밝힌다.
  - Traceback 은 블록 전체를 유지한다. 마지막 줄이 실제 예외다.
  - 같은 줄이 반복되면 한 번만 보여 주고 "(N회 반복)"으로 줄인다.
- **원인 찾기**: 시간순으로 **가장 처음 나온 오류**를 근본 원인 후보로 본다. 그 뒤 오류는 연쇄 결과일 가능성이 높다고 구분해서 알린다.
- **출력 형식**
  ```
  [Relevant Logs Only] 전체 N줄 중 M줄
  Error: line 245  <그 줄 내용>
  (앞뒤 맥락 몇 줄)
  ```
  그다음 분석(무슨 오류인지, 가능한 원인, 확인 순서)을 쓴다.
- **누락 방지**: 추린 기준(키워드)과 제외한 줄 수를 한 줄로 밝혀, 사용자가 빠진 게 있는지 판단할 수 있게 한다. 오류 키워드가 하나도 없으면 억지로 찾지 말고 "오류 표시가 없습니다. 어떤 증상인지 알려 주세요."라고 되묻는다.
- **비밀정보**: 로그에 토큰·키·비밀번호·이메일·사용자 이름 경로가 보이면 출력에서 `***`로 가린다.

## 큰 요청의 단계 분해

"전체 로그인 시스템 다 만들어줘"처럼 한 번에 끝낼 수 없는 요청은 사용자가 단계를 말하지 않아도 스스로 나눈다.

- **큰 요청 판단**: 여러 파일·기능이 필요하다, 설계 선택(방식·구조)이 필요하다, 되돌리기 어려운 변경이 있다 중 하나라도 해당하면 큰 요청으로 본다. 작은 요청은 나누지 않는다.
- **세 단계로 나눈다**:
  1. **분석**: 현재 코드·폴더·환경에서 이미 있는 것과 없는 것을 확인한다. (코드로 확인 가능한 건 묻지 않고 직접 본다.)
  2. **문제 설명**: 무엇이 필요하고 어디가 어려운지, 선택지와 장단점(예: 세션 방식 vs 토큰 방식)을 쉬운 말로 정리한다. 선택이 필요한 지점은 추천안을 먼저 제시한다.
  3. **해결 방법**: 구현 계획을 작은 작업 순서로 쪼개 보여 준다. 구현은 이 계획을 승인받은 뒤 시작한다.
- 승인 후 한 번에 몰아서 만들지 않고, 작업 단위마다 실행과 확인(실행·테스트 결과)을 보고하며 진행한다.
- 파일이 많이 바뀌는 작업은 시작 전에 브랜치를 만들거나 되돌릴 방법을 안내한다.

## 전달력 점검

사용자가 쓴 **원래 입력**이 AI에게 잘 전달되게 작성됐는지 평가해 알려 준다. 평가는 사용자가 쓴 글만 기준으로 한다. Claude가 직접 읽어서 알게 된 맥락(파일 내용 등)은 점수에 넣지 않는다.

- **5개 항목, 항목당 1점**
  1. 목표: 원하는 결과가 드러난다. (예: "원인을 찾아줘", "성능을 개선해줘")
  2. 대상: 다룰 파일·코드·문서가 지정돼 있다.
  3. 맥락: 현재 상태나 에러, 환경 중 하나 이상이 적혀 있다.
  4. 제약: 범위·금지 사항·형식·기한 중 하나 이상이 적혀 있다.
  5. 초점: 요청이 하나로 좁혀져 있다. (여러 요청이 뒤섞이지 않았다)
- **등급**: 4~5점 "잘 전달됨", 2~3점 "보통", 0~1점 "보완 필요".
- 각 항목에 ✓/✗를 달고 **사용자가 쓴 말을 근거로 한 줄**씩 적는다. 근거 없이 ✗만 쓰지 않는다. ✗ 항목에는 채우는 예시 한 구절을 붙인다.
- 점수는 기록 명령의 `score`에 넣는다.
- 평가는 사실만 쓴다. 칭찬·훈계·가혹한 표현은 쓰지 않는다. 입력이 이미 충분하면 "충분히 전달됩니다"라고 짧게 쓴다.

## 출력 형식

**원래 입력**
> (사용자가 쓴 글 그대로)

제 역할은 (역할)이고 (중점) 중심으로 답하겠습니다.

**정리된 요청**
[ROLE] (역할) — (중점) (근거: ...)
[GOAL] ...
[CONSTRAINTS] ...
[CONTEXT] ...
[QUESTION] ...

**단계 계획** (큰 요청일 때만)
1. 분석: ...
2. 문제 설명: ...
3. 해결 방법: ...

**전달력 점검: N/5 (등급)**
- ✓/✗ 목표: (근거)
- ✓/✗ 대상: (근거)
- ✓/✗ 맥락: (근거)
- ✓/✗ 제약: (근거)
- ✓/✗ 초점: (근거)

**이렇게 물으면 됩니다** (복사해서 바로 쓸 수 있는 자연스러운 한 문단)
> (정리된 요청을 라벨 없이 평소 말투의 문장으로 다시 쓴 것)

**배울 점** (2~3개)
- 무엇을 보강했는지와 **왜 그것이 답의 품질을 바꾸는지**를 한 줄씩 쓴다. 예: "어떤 에러가 나는지 적으면 원인을 바로 좁힐 수 있습니다."
- 사용자가 다음에 스스로 쓸 수 있도록 **빠뜨리기 쉬운 항목**(맥락, 제약, 원하는 결과)을 짚어 준다.
- 칭찬이나 훈계는 하지 않고 사실만 쓴다.

## 하지 말 것

- 입력에 없는 제약·맥락을 사실처럼 채워 넣는 것. 모르면 비워 두고 되묻는다. (ROLE 은 예외이며 판단 근거를 함께 적는다.)
- 근거 없이 화려한 역할을 붙이는 것. 코드·요청에서 확인되는 만큼만 정한다.
- 한 줄로 충분한 단순한 요청까지 다섯 항목으로 늘리는 것. 단순하면 "이대로 충분합니다"라고 알리고 바로 실행한다.
- 작은 요청까지 단계로 쪼개는 것.
- "배울 점"에 일반론(예: "명확하게 쓰세요")을 쓰는 것. 이번 입력에서 실제로 빠졌던 것만 짚는다.
- 승인 전에 파일 수정·삭제·커밋 같은 실행을 하는 것. 큰 요청은 단계 계획 승인 전에 구현을 시작하지 않는다.
- 장황한 서론과 마무리 요약.
